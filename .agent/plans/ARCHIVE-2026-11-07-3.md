This project builds new features under contracts (.agent/contracts/<feature>.md). A new code file needs an entry here whose
Feature has an open contract and whose Criterion names one of that contract's acceptance criteria.

### core/src/edit_schedule/schedule_safety.rs
**Purpose:** Evaluates whether an outsideHours schedule change loosens across all minutes, days, and daylight-saving transitions.
**Feature:** edit-block-schedule
**Existing code checked:** `rg -n closes_outside_hours core/src` shows existing rule closure evaluation logic for outsideHours rules.
**Failure paths:** Missing rules, invalid stretches, empty day lists, and overnight boundary ambiguities default safely to loosening.
**Criterion:** AC-004: schedule edit may bypass locks only if rule cannot change from closed to open.
**Split justification:** Safety validation across time zones and decision minutes is separate from rule replacement and lock planning.

### core/src/edit_schedule/rule_edit.rs
**Purpose:** Modifies the days and allowed stretches of an existing outsideHours rule within a validated block settings structure.
**Feature:** edit-block-schedule
**Existing code checked:** `rg -n apply_coverage_zip core/src` shows how the block coverage editor updates block fields in settings zips.
**Failure paths:** Unknown block or rule IDs, non-outsideHours rule kinds, overlapping stretches, and zip validation errors return descriptive errors without modifying data.
**Criterion:** AC-002: schedule edit changes only the named outside-hours rule and refuses invalid requests.
**Split justification:** Modifying block rule structures in zip archives is a distinct responsibility from time-based safety analysis.

### core/src/edit_schedule/schedule_plan.rs
**Purpose:** Evaluates schedule changes against block and routine locks to determine whether changes land immediately or must wait.
**Feature:** edit-block-schedule
**Existing code checked:** `rg -n plan_edit core/src` shows the lock planning logic that inspects block and routine locks for delayed execution.
**Failure paths:** Blocks with required partner keys, missing blocks, incompatible lock periods, and loosening changes result in appropriate wait plans or refusal.
**Criterion:** AC-005: tightening changes land immediately while loosenings are parked under block and routine locks.
**Split justification:** Lock planning coordinates applicable locks and wait calculations separately from rule JSON editing.

### cli/src/edit_schedule/schedule_arguments.rs
**Purpose:** Parses command-line arguments for the edit-schedule command into structured options without side effects.
**Feature:** edit-block-schedule
**Existing code checked:** `rg -n read_edit_arguments cli/src` shows the argument parser for block editing options.
**Failure paths:** Missing file, block, or rule identifiers, invalid time stretch formats, unknown weekdays, and duplicate flags fail with usage errors.
**Criterion:** AC-001: schedule preview accepts open-hours and days flags and displays old and proposed rules without writing.
**Split justification:** Command line argument parsing is decoupled from disk operations, zip parsing, and business logic.

### cli/src/edit_schedule/run_edit_schedule.rs
**Purpose:** Executes the edit-schedule CLI command workflow, presenting dry-run previews or performing atomic writes and queue parking.
**Feature:** edit-block-schedule
**Existing code checked:** `rg -n run_edit_block cli/src` shows the execution flow for previewing, writing immediately, or queueing delayed changes.
**Failure paths:** IO errors, corrupt settings or waiting files, missing targets, and lock delays without the write flag are handled without corrupting files.
**Criterion:** AC-006: schedule edits save immediately with write flag or park in waiting queue without touching the zip.
**Split justification:** CLI coordination and user reporting are distinct from pure argument parsing and core domain models.
